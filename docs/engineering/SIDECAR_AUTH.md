# Sidecar authentication (Phase 77/78)

Status: design fixed 2026-10-06; implementation tracked in `TODO.md` §77/78 and
`RISK_REGISTER.md` R013/R014. This file is the single source of truth for the wire
protocol — the code, the tests and the briefs all point here.

## Problem

Both sidecars (torch `127.0.0.1:7421`, LLM `127.0.0.1:7422`) listen on loopback
without authentication and answered every request with `Access-Control-Allow-Origin: *`.
Any web page the user visits could therefore `fetch()` them from the browser
(`/infer` executes Custom-layer code, `/run_workspace_script` runs scripts, `/respond`
approves a pending "run this script?" confirmation, `/chat` drives an LLM that holds the
user's API key). On a shared HPC login node the remote sidecar's loopback port is
reachable by every other user of the node. A DNS-rebinding page defeats a naive
"loopback only" assumption.

## Model

One 256-bit random token per app launch, generated by the Rust shell (OS randomness),
handed to the managed sidecars through the **environment** of the spawn, and to the
webview through the Tauri command `sidecar_token`. Every request except `OPTIONS` and
`GET /health` must carry it in the header `X-SpinoML-Token`. In addition every request is
checked against a `Host` and `Origin` allow-list, so a browser page cannot reach the
sidecar even when no token is configured (browser-dev mode).

### Configuration (environment, both sidecars, read once at startup)

| variable | meaning |
|---|---|
| `SPINOML_SIDECAR_TOKEN` | the token. Must be ≥ 32 chars of `[A-Za-z0-9_-]`; otherwise the sidecar **refuses to start (exit 2)** with a message that never prints the value. Unset = mode `unauthenticated-dev`. |
| `SPINOML_REQUIRE_TOKEN=1` | token mandatory: unset/empty token → exit 2 (used by the managed launches and CI). |
| `SPINOML_ALLOWED_ORIGINS` | optional comma-separated list of EXTRA origins, exact string match, no wildcards. |

After reading, the sidecar **removes `SPINOML_SIDECAR_TOKEN` from its own process
environment** (`os.environ.pop` / `delete process.env[...]`) so no child process it spawns
(pip, scripts, sbatch, opencode, the Claude CLI) inherits it. Residual: a process of the
same OS user can still read `/proc/<pid>/environ` of the sidecar (see Limits).

### Default origin allow-list (exact match)

`tauri://localhost`, `http://tauri.localhost`, `https://tauri.localhost`,
`http://localhost:5173`, `http://127.0.0.1:5173` (+ `SPINOML_ALLOWED_ORIGINS`).

### Per-request enforcement order (identical in both sidecars)

1. **Host** (both modes): the host part of the `Host` header (port stripped, `[::1]`
   handled, case-insensitive) must be one of `127.0.0.1`, `localhost`, `[::1]`. Missing or
   other → `403`, `code: "bad_host"`. (Any port is accepted: the remote sidecar is reached
   through an ssh tunnel whose local port differs from its own. DNS rebinding needs a
   non-loopback hostname, which this rejects.)
2. **Origin** (both modes): if an `Origin` header is present it must be an exact member of
   the allow-list (the literal `null` is NOT allowed) → else `403`, `code: "bad_origin"`,
   and NO CORS headers on that response. No `Origin` header (curl, Python, the MCP bridge,
   the Rust app, tests) is allowed.
3. **`OPTIONS`**: `204`. With an allowed Origin: `Access-Control-Allow-Origin: <that origin>`
   (never `*`), `Vary: Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers:
   Content-Type, X-SpinoML-Token`, `Access-Control-Max-Age: 600`. No token needed (browsers
   do not send custom headers on a preflight).
4. **`GET /health`**: no token needed. Body in mode `token`: without/with a wrong token
   exactly `{"ok": true, "auth": "token", "requiresAuth": true, "tokenOk": false}` (no
   version/scope/other info); with the right token the existing full body plus the same three
   keys with `tokenOk: true`. Mode `unauthenticated-dev`: existing full body plus
   `"auth": "unauthenticated-dev", "requiresAuth": false, "tokenOk": true`.
   **Exception (LLM sidecar only): `POST /internal/mcp/<requestId>/list|call`** skips the
   master-token requirement of this step (Host and Origin above still apply): the opencode
   MCP bridge is a child of the opencode process the model drives and must never hold the
   master token. That route is authenticated by the per-turn session secret (see "LLM
   sidecar specifics"), in BOTH modes, and the master token is NOT accepted there.
5. **Everything else**: mode `token` → exactly one `X-SpinoML-Token` header, compared in
   constant time (`hmac.compare_digest` / `crypto.timingSafeEqual` after a length-safe
   digest of both sides) → else `401`, `code: "unauthorized"`, `reason: "missing" | "invalid"`.
   The body is NOT read before this check passes.
6. Responses to a request with an allowed Origin carry the Origin echo (+ `Vary: Origin`)
   including the 401/4xx error responses, so the webview can read them. Responses to a
   request without Origin carry no CORS headers.

Error bodies use each sidecar's existing error convention plus the machine-readable
`code`. The token value is never logged, echoed or included in any error message; rejected
requests log at most `method path code` (no headers).

### LLM sidecar specifics

* Protected like everything else: `/chat`, `/respond`, `/opencode/models`.
* `requestId` and `askId` become `crypto.randomUUID()` (were counters `req1`, `req1:1`).
* `/internal/mcp/<requestId>/list|call` (the opencode MCP bridge) is authenticated with a
  **per-turn session secret** (`randomBytes(32)` hex, stored in the `mcpSessions` entry,
  compared in constant time), NOT the master token — the master token never reaches the
  opencode process. Required in BOTH modes. The secret reaches the bridge through the
  `environment` of the opencode `mcp.graph` config entry (`SPINOML_MCP_SECRET`), never argv
  (`ps` is world-readable). The bridge sends it as `X-SpinoML-Token` and prints a clear
  stderr line on a 401.

### Rust shell

* `getrandom` 32 bytes → 64 hex chars, generated once at startup into managed state
  `SidecarTokens { local, remote }`. `SidecarTokens` has no `Debug`/`Display`; tokens are
  never logged.
* `spawn_managed` sets `SPINOML_SIDECAR_TOKEN` + `SPINOML_REQUIRE_TOKEN=1` via
  `Command::env` for BOTH sidecars (not process-global `set_var`).
* Tauri command `sidecar_token(endpoint: String) -> Result<Option<String>, String>` with
  endpoint `"torch-local" | "llm" | "torch-remote"`; unknown endpoint → `Err`. `"torch-remote"`
  returns `Some` only while a remote sidecar started by this app session is alive.
* Remote sidecar: a fresh token per `ensure_remote_sidecar` run, **delivered through ssh
  stdin** (never argv, never the remote command string, never a file): the remote script
  starts with `IFS= read -r SPINOML_TOK` into a NON-exported shell variable (so `env.sh`
  and anything it starts do not inherit it), sources `env.sh`, and only then does
  `export SPINOML_SIDECAR_TOKEN="$SPINOML_TOK" SPINOML_REQUIRE_TOKEN=1; unset SPINOML_TOK`
  immediately before `exec`ing python — so `env.sh` cannot replace the token with its own
  value either. The Rust side writes `token\n` to the child's stdin and keeps the handle
  open for the lifetime of the session. An empty read aborts the start before python runs
  (`[ -n "$SPINOML_TOK" ] || exit 11`); the sidecar would otherwise also refuse to start via
  `SPINOML_REQUIRE_TOKEN`.
* Remote deploy ships EVERY file the sidecar needs (see "Remote deploy file list").

### Frontend

`src/sidecars/auth.ts`: the only place that talks to `sidecar_token` and the only
wrapper for sidecar requests (`sidecarFetch`). It adds the header when a token exists
(Tauri mode), on `401` drops the cached token, re-reads it and retries ONCE, then throws
`SidecarAuthError` (also on `403`, message names Origin/Host). A static check
(`scripts/verify-sidecar-fetch.ts`) fails when any `src/` file calls bare `fetch` against a
sidecar URL. Health probes distinguish `online | offline | auth-failed` and surface
`auth: "unauthenticated-dev"` (header badge tooltip, plus a visible warning when a Tauri
build talks to a tokenless sidecar). Auth failures must never be reported as "offline".

## Remote deploy file list (regression found while designing this phase)

`remote_sidecar.rs::deploy` uploads only `main.py` and `dataset_handlers.py`, but since
Phase 45–47 `main.py` also imports `scope`, `safe_load`, `deps_policy` (and Phase 78 adds
`auth`), and the ESPF tokenizer reads `sidecar-torch/espf/*`. A remote sidecar would die with
`ModuleNotFoundError` on start. The deploy list is now ONE constant in Rust and a static
test (`scripts/verify-remote-deploy-files.ts`) computes the local-import closure of
`sidecar-torch/*.py` + the runtime data files and fails when the constant misses any.

## Honest limits (documented in LIMITATIONS.md)

1. A process of the same OS user can read the token (`/proc/<pid>/environ`, the app's
   memory) — same-user compromise is out of scope.
2. The webview can call `sidecar_token` and every other Tauri command: any script running
   in the app origin (XSS, a compromised CDN script) wins. `tauri.conf.json` has
   `"csp": null` and `@monaco-editor/react` loads Monaco from `cdn.jsdelivr.net` at
   runtime (R052). A strict CSP needs a real-webview test and bundled Monaco → TODO, not
   done here.
3. The token is per launch; there is no rotation inside a session and no revocation.
4. Browser-dev mode (`npm run dev` + manually started sidecars) runs `unauthenticated-dev`
   unless the developer exports a token; Host/Origin checks still apply.
5. No TLS (loopback / ssh-tunnel only).
